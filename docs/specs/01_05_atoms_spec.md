# 01_05 Atoms Specification

> **Status**: DRAFT (V-Next Revision)
> **Owner**: Architecture Team
> **Context**: Definition of the fundamental elements of Flows in the Flow Manager ecosystem.

## 1. Overview
**Atoms** are the fundamental, indivisible elements of a *Flow*. They are the smallest, atomic blocks that make up a directed execution graph.

**CRITICAL ARCHITECTURAL DISTINCTION: Atoms vs. Tools**
*   **Tools** are MCP-like (Model Context Protocol) capabilities consumed directly by an *Agent* during its reasoning loop.
*   **Atoms** are the smallest building blocks of *Flows* orchestrated by the Engine.
*   **BOTH** Atoms and Tools can be *Active* (manipulating files, triggering deployments, mutating state) or *Passive* (reading data, validating status, searching knowledge).

**Shared Infrastructure Layer (`src/flow/infrastructure/`):**
While Atoms and Tools serve entirely distinct Domain purposes (Orchestration vs. Agent Capabilities), they MUST **not** duplicate low-level code. Both `src/flow/atoms/` and `src/flow/tools/` act as lightweight Domain Wrappers that import from a shared core infrastructure layer.
*   **Surgical Editing (`Loom`)**: Used by both `FileTool` and active `TransformAtoms`.
*   **Process Isolation (`ProcessSupervisor`)**: Used by `ShellTool` and `ScriptAtom`.
*   **Stream Security (`SmartRedactor`)**: Used by `FileTool` and network `WebhookAtoms`.
*   **Vector DB (`Qdrant` Client)**: Used by `KnowledgeTool` and semantic-aware Engine components.

**Key Characteristics of an Atom:**
1.  **Strictly Stateless**: Atoms must retain ZERO internal state between or during executions. The FLOW ENGINE is entirely responsible for tracking the successful and failed runs of Atoms.
2.  **Deterministic Run IDs (Fixed Input)**: Atoms are executed within the context of a dedicated, computable `Run ID` generated by the Engine. This ID must be deterministically hashable based on **static** parameters (e.g., `hash(AtomType + FlowVersionHash + Config + ParentFlowID + LoopIndex + RetryCount)`). **CRITICAL**: The ID MUST NOT include runtime/context variables or non-deterministic elements like `timestamps` or `UUIDs`. Using a timestamp breaks the ability to reliably cache and resume previous identical runs. Including a `FlowVersionHash` prevents stale Execution State from resuming if the developer modifies the underlying YAML/Flow definition during a pause. The Engine Native State handles runtime variables, while injecting the structural `loop_index` into the hash guarantees uniqueness across loops/retries without breaking determinism.
3.  **State Boundaries**: An Atom execution represents a discrete step. The Flow Engine persists state before an Atom begins and after an Atom completes via the `AtomResult`.
4.  **No Sub-Flow Orchestration**: Atoms are completely ignorant of the overall Flow DAG. They process inputs, perform an action, and yield outputs. They **never** instantiate or route sub-flows.
5.  **Not Inherently Idempotent**: *Active* Atoms (like `AgentAtom`, `ScriptAtom`) execute real-world side effects. They are inherently NOT idempotent. The system relies on the Engine's `Run ID` execution locks and strictly sequential routing to ensure they run "Exactly Once", enforcing structural isolation to prevent split-brain overlaps. For non-deterministic outputs (like LLMs), the Engine MUST implement a **Write-Around Memoization Cache** keyed by the `Run ID`. Active file mutations must utilize **Atomic Check-Then-Act** patterns (e.g., counting matches before appending) to guarantee true idempotency upon Orchestrator restart.
6.  **Isolated Fault Domains**: Atoms catch all internal exceptions and yield a structured state (`AtomResult`), preventing Orchestrator crashes.
7.  **Typed Contracts**: Atoms strictly define their required Config (static) and Context (runtime) schemas.

## 2. The Base Protocol (`Atom`)
Located at: `src/flow/atoms/__init__.py`

All Atoms must inherit from this Abstract Base Class.

```python
from enum import Enum
from abc import ABC, abstractmethod
from typing import Any, Dict, Optional

class AtomStatus(str, Enum):
    SUCCESS = "SUCCESS"     # Action completed as intended
    FAILED = "FAILED"       # Action failed permanently
    WAITING = "WAITING"     # Suspended, waiting for human approval or async callback
    RETRY = "RETRY"         # Transient failure, Engine should retry based on strategy

class AtomResult:
    def __init__(
        self, 
        status: AtomStatus, 
        message: str, 
        exports: Optional[Dict[str, Any]] = None,
        error: Optional[Dict[str, Any]] = None
    ):
        self.status = status       # The state machine transition signal
        self.message = message     # Human-readable summary for logs
        self.exports = exports or {} # Data to write back to the Global Flow Context
        self.error = error         # Structured error context for debugging/telemetry
```

> **CRITICAL: Context Memory Limits (OOM Prevention)**
> To prevent massive dictionaries from lagging the Engine's disk-syncing loop, `exports` must **never** contain large strings (e.g., full source files, multi-megabyte LLM context dumps).
> *   **Limit**: Direct string payloads inside `exports` should be capped at `128KB` aggregate.
> *   **Blob Pointers**: For large outputs, the Atom must write the string to `.flow/artifacts/blob_{uuid}.txt` and return a lightweight pointer in `exports` (e.g., `{"file_diff_ref": "blob_1234"}`). If the Atom encounters an `IOError` during this write (e.g., Disk Full), the Atom MUST catch the error and yield an `AtomResult(status=AtomStatus.FAILED, error=IOContext)`.

```python
class Atom(ABC):
    @abstractmethod
    def run(self, context: Dict[str, Any], config: Dict[str, Any]) -> AtomResult:
        """Executes the discrete unit of work."""
        pass
        
    def cleanup(self) -> None:
        """
        Graceful teardown hook (e.g., closing subprocesses/sockets).
        The Engine MUST wrap this call in an independent `try/except` block to guarantee 
        that a failure here does not abort the broader Flow teardown sequence.
        """
        pass

    def compensate(self, context: Dict[str, Any], config: Dict[str, Any], run_id: str) -> None:
        """
        Saga Pattern Rollback Hook.
        If a downstream Flow step fails completely, the Engine invokes this method 
        traversing backwards to clean up dirty state (e.g., dropping temp tables, deleting draft PRs).
        For local file mutations, the Orchestrator MUST mandate a Pre-Flight Git Commit before starting 
        the Saga, allowing `compensate()` to perform a flawless `git reset --hard` and `git clean -fd` 
        rather than relying on fragile procedural undo logic.
        
        [PROPOSAL - FUTURE]: If this method raises an unhandled exception, the Flow MUST be 
        transitioned to a `FATAL_INCOMPLETE_ROLLBACK` state for manual SRE remediation.
        """
        pass
```

### 2.1 The Context vs Config Split
*   **`config`**: Immutable parameters defined in the Flow YAML (e.g., `retries: 3`, `target_branch: main`).
*   **`context`**: Malleable runtime state populated by previous Atoms in the pipeline (e.g., `previous_step_artifact_path`).

## 3. The `AgentAtom` (Cognitive Execution)

While many Atoms will be procedural (e.g., `GitCommitAtom`, `SendNotificationAtom`), the highest-complexity Atom is the `AgentAtom`.

### 3.1 Purpose
The `AgentAtom` acts as an integration "Hull" or "Shell". It does not directly manage LLM APIs or execute raw system commands. Instead, it tightly binds the **LLM Binding System (`01_06`)** and the **Tooling System (`01_04`)** to achieve a dynamic objective. It embeds stochastic Agentic reasoning into a deterministic Flow.

Its primary responsibility as an Orchestrator Atom is **State Boundary Management and Idempotency**: isolating the external systems, hydrating the LLM ReAct loop on a resume, and catching exceptions from the external boundaries to prevent Engine crashes. 

### 3.2 Resilience & The ReAct Loop
A ReAct (Reason-Act) loop is stochastic and can run for minutes, consuming multiple Tools. If the Flow Engine stops mid-loop, starting the `AgentAtom` from scratch destroys progress and wastes tokens.

### 3.3 The AgentAtom Contract
To satisfy the Orchestrator's need for discrete state boundaries, the `AgentAtom` must:
1.  **Persist Thought History**: After *every single Tool invocation* within its ReAct loop, the `AgentAtom` must serialize its scratchpad/message history back to the Engine.
2.  **Re-entrant `run()` via Run ID**: If `run()` is called, it first checks the `context` for existing serialized history. If found, it natively resumes the ReAct loop from the exact point of interruption rather than restarting the prompt. 
    *   **CRITICAL (Tool Exactly-Once Execution)**: Tools are inherently side-effecting. The `AgentAtom` relies on the Engine's Tool-level transactional checkpointing (as defined in `01_04_tooling_spec`) to prevent duplicate tool execution upon ReAct loop resumption. It also relies on the Engine's external structural isolation to guarantee safe concurrent execution.
3.  **Sequential DAG Injection for Subflows**: If the `AgentAtom` determines a new *Subflow* needs to be executed, it yields a dynamic DAG output and FINISHES (yields `SUCCESS`). The Engine router injects the subflow as the *next* sequential step in the DAG. A *subsequent* AgentAtom step must digest the subflow result. Re-animating a completed Atom run breaks the DAG's forward-only momentum and is strictly prohibited.
4.  **Atomic Indivisibility**: The AgentAtom is a single point of execution. Despite taking minutes to run and triggering thousands of tokens, it is structurally just one node. It MUST NEVER trigger a Subflow directly. Orchestrating subflows is the domain of the Engine DAG.

## 4. Procedural Orchestration Atoms

In addition to `AgentAtom`, a Flow will consist of procedural Atoms handling logic and state. 

### 4.1 `ManualReviewAtom` (Quality Gates & Pausing)
*   **Purpose**: Intentional pausing / Quality Gates.
*   **Behavior**: Returns `AtomResult(status=AtomStatus.WAITING)`. The Engine serializes state to `.flow_state/` and suspends the daemon listener, awaiting an external API trigger (like a Human clicking "Approve" in a UI or CLI) to unpause the parent Flow.
*   **Note**: This is distinct from an Agent using an `ask_human` Tool. This is a rigid, Orchestrator-level pause between discrete Flow steps.

### 4.2 `AssertionAtom` (Deterministic Quality Gate)
*   **Purpose**: A hardcoded programmatic check.
*   **Behavior**: Evaluates a strict rule against the `context` (e.g., `coverage_percentage >= 80`). If the rule fails, the Atom yields `AtomStatus.FAILED` and halts the Flow. If it passes, it yields `SUCCESS`.

### 4.3 `TransformAtom` (Data Mapping)
*   **Purpose**: Adapting data between steps without needing an LLM.
*   **Behavior**: Executes a lightweight JSONPath/JMESPath query against the `context` to extract or restructure data, saving the result to `exports`. Acts as glue between standard Atoms.

### 4.4 `WebhookAtom` (System Integration)
*   **Purpose**: Asynchronous system notification or triggering.
*   **Behavior**: Executes a standard HTTP REST call (e.g., to Slack, Jira, or a CI/CD pipeline) based on fixed `config` parameters. Returns `SUCCESS` if the external system acknowledges the webhook.

### 4.5 `ScriptAtom` (Subprocess Execution)
*   **Purpose**: Running deterministic, local scripts or shell commands without expensive Agent overhead.
*   **Behavior**: Executes a command defined in `config` (e.g., `pytest`, `npm ci`, `docker build`) within a bounded subprocess. Captures `stdout`, `stderr`, and `exit_code`, mapping them into `exports`. Includes a strict timeout to prevent zombie processes.
*   **Safety (Process Isolation)**: MUST execute out-of-process. The specific isolation mechanism (Job Objects, cgroups) is strictly an Engine-level concern (managed by the `ProcessManager`), preventing infrastructure details from leaking into the Atom Domain protocol. This guarantees that host crashes or memory leaks do not bleed into the Orchestrator Engine.

### 4.6 `SingleShotLLMAtom` (Narrow Intelligence)
*   **Purpose**: Applying NLP classification or summarization without the unbounded, expensive overhead of a full ReAct loop or tool integration.
*   **Behavior**: Accepts a simple `prompt_template`, interpolates runtime `context` variables, calls the LLM Binding once, returns the string output in `exports`, and instantly completes.

## 5. Non-Atoms (Engine Concerns)

To prevent anti-patterns and redundant proxy classes, the following common orchestration needs are explicitly **NOT** Atoms. They are native features of the Flow Engine DAG Router:

1.  **State Suspension (Waiting/Timers)**: Pausing a DAG context while waiting for an external HTTP webhook or a network timer to expire is not "work"; it is an Orchestration mechanic. There are no `AwaitCallbackAtoms` or `TimerAtoms`. The Engine pauses execution natively via special declarative flow steps (e.g., `- type: await_webhook`).
2.  **Sub-Flows**: A Flow calling another Flow is handled by the Engine recursively loading the requested DAG. There is absolutely NO `SubFlowAtom`. Atoms are indivisible and completely ignorant of sub-flows. This hierarchical state management and resumption is fully detailed in `01_09_flows_spec.md`.
3.  **Routing (Switch/Case)**: Determining which execution branch to take based on a variable is a fundamental DAG traversal feature, managed by the Engine.
4.  **Parallelism (Map/Fan-Out)**: Executing a single task concurrently across a list of items is managed by the Engine splitting the execution thread, not by an Atom attempting to manage parallel subprocesses.
5.  **Parallel Fan-In (Reducers) & Orthogonality**: Merging outputs from multiple parallel branches back into the parent `context` is a structural Engine routing concern. To prevent data race conditions, the Engine MUST enforce that parallel paths are strictly **Orthogonal** (writing to discrete files or explicit sub-domains like `exports["qa_review"]`). It is strictly forbidden for parallel branches to blindly race to update the same shared context keys. A subsequent, sequential `ReducerAtom` or `AgentAtom` must be implemented in the DAG immediately following the parallel block to synthesize and resolve the orthogonal results.

## 6. Lifecycle & Sandboxing Guarantees

Every derived `Atom` must adhere to these guarantees:

### 6.1 Exception Bleeding (The "Iron Wall")
The `run()` method is wrapped by the Engine in an aggressive `try/except Exception` block. If an Atom throws a standard Python error (e.g., `KeyError`, `IndexError`), the Engine catches it, logs a stack trace, and enforces an `AtomStatus.FAILED` state.
*   **Edge Case**: Native `try/except Exception` does not catch `BaseException` (like `SystemExit` or `KeyboardInterrupt`). If an Atom calls `sys.exit(1)` or crashes the host with a C-extension segfault, the Orchestrator will instantly die.

### 6.2 Graceful Teardown (Hard Timeout & Recursive Tracing)
If the Flow Engine receives a `SIGTERM` or cancellation trigger, it iterates over the currently active Atom and explicitly calls `cleanup()`. 
*   **Recursive Stack Traversal**: For fractal subflows (e.g., Flow A -> Subflow B -> Atom C), the Engine MUST walk the entire call stack upwards, executing the `cleanup()` and/or `compensate()` hooks of every parent flow container, as parents might hold broad resource locks independent of the leaf Atom.
*   **Deadlock Prevention**: The Engine MUST use signal-based interruption (e.g., `SIGALRM`) or process-level `.terminate()` to guarantee Orchestrator teardown. Native Python thread timeouts (`.join(5)`) do not forcefully interrupt blocking C-extensions or network sockets. Relying solely on thread timeouts will lead to zombie orchestrators holding system resources during a teardown.

## 7. Lineage & Audit Tracking

Because Atoms represent discrete state boundaries in the Orchestrator, they form the natural resolution for Lineage and Audit tracking (documenting who did what, why, and when).

### 7.1 Phase 1: File-Based Audit Log (Current)
To support the V-Next file-based `.flow_state/` system, the Engine enforces an immutable append-only `audit.jsonl` log parallel to the `context.json`.
*   **Mechanism**: Every time an Atom yields an `AtomResult`, the Engine automatically calculates a state diff and appends a structured Lineage Entry. The log is strictly for LINEAGE; micro-step traces from inside `AgentAtom` loops do NOT pollute the audit log and are relegated to ephemeral trace logs.
*   **Payload Example**:
    ```json
    {
      "timestamp": "2026-02-22T23:05:00Z",
      "flow_id": "req-1234.subflow-A",
      "atom_type": "AgentAtom",
      "run_id": "deterministic-hash-abc",
      "state_transition": "WAITING -> SUCCESS",
      "message": "Approved by Human",
      "mutated_keys": ["review_status", "coverage"],
      "correlation_id": "abcd-efgh"
    }
    ```

> *Note: Phase 2 (Database-Backed Event Sourcing) is planned for the roadmap. See `docs/plans/roadmap_2026.md` (Phase 1.5).*
