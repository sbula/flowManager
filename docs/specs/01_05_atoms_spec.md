# 01_05 Atoms Specification

> **Status**: DRAFT (V-Next Revision)
> **Owner**: Architecture Team
> **Context**: Definition of the fundamental elements of Flows in the Flow Manager ecosystem.

## 1. Overview
**Atoms** are the fundamental, indivisible elements of a *Flow*. They are the smallest, atomic blocks that make up a directed execution graph.

**CRITICAL ARCHITECTURAL DISTINCTION: Atoms vs. Tools**
*   **Tools** are MCP-like (Model Context Protocol) capabilities consumed directly by an *Agent* during its reasoning loop.
*   **Atoms** are the smallest building blocks of *Flows* orchestrated by the Engine.
*   **BOTH** Atoms and Tools can be *Active* (manipulating files, triggering deployments, mutating state) or *Passive* (reading data, validating status, searching knowledge).

**Shared Infrastructure Layer (`src/flow/infrastructure/`):**
While Atoms and Tools serve entirely distinct Domain purposes (Orchestration vs. Agent Capabilities), they MUST **not** duplicate low-level code. Both `src/flow/atoms/` and `src/flow/tools/` act as lightweight Domain Wrappers that import from a shared core infrastructure layer.
*   **Surgical Editing (`Loom`)**: Used by both `FileTool` and active `TransformAtoms`.
*   **Process Isolation (`ProcessSupervisor`)**: Used by `ShellTool` and `ScriptAtom`.
*   **Stream Security (`SmartRedactor`)**: Used by `FileTool` and network `WebhookAtoms`.
*   **Vector DB (`Qdrant` Client)**: Used by `KnowledgeTool` and semantic-aware Engine components.

**Key Characteristics of an Atom:**
1.  **Strictly Stateless (With One Accepted Compromise)**: Atoms must generally retain ZERO internal state between executions, relying on the Flow Engine to track successful and failed runs. The designated exception is the `AgentAtom`, which is allowed to persist its serialized "thought history" to bridge the gap between stochastic reasoning loops and deterministic Orchestrator boundaries.
2.  **Deterministic Run IDs (Fixed Input)**: Atoms are executed within the context of a dedicated, computable `Run ID` generated by the Engine. This ID must be deterministically hashable based on **static** parameters (e.g., `hash(AtomType + FlowVersionHash + Config + ParentFlowID + DAG_NodeID + LoopIndex + TriggerEventID)`). The explicit inclusion of `DAG_NodeID` (or `StepIndex`) guarantees that identical parallel tasks do not suffer from hash collisions. The explicit inclusion of `TriggerEventID` or `RootInstanceUUID` guarantees that concurrent executions of the exact same flow shape by multiple users remain universally disjointed, preventing state-database cross-pollution. **CRITICAL**: The ID MUST NOT include runtime/context variables, `timestamps`, or `UUIDs`.
    *   **Idempotency vs Retries**: The core `Run ID` (Base Identity Hash) strictly identifies the *intent* of the step. The `RetryCount` MUST NOT be included in this Base Hash. Instead, retries must be recorded under this Base Hash. This allows a retry attempt to successfully lookup and recover a partially completed external network call from the memoization cache.
3.  **State Boundaries**: An Atom execution represents a discrete step. The Flow Engine persists state before an Atom begins and after an Atom completes via the `AtomResult`.
4.  **No Sub-Flow Orchestration**: Atoms are completely ignorant of the overall Flow DAG. They process inputs, perform an action, and yield outputs. They **never** instantiate or route sub-flows. Agents also **do not spawn subflows**.
5.  **Reconciliation Loop Principle (Idempotency Contract)**: Active Atoms execute side effects and are difficult to make idempotent. We explicitly abandon complex Imperative Sagas and rollbacks. By shifting from a linear execution script to a Desired State Map, the system natively handles crash recoveries, greenfield execution, and brownfield deployments identically: it analyzes the state of the world *right now* and moves forward. This fundamentally resolves the trap of deleting the results of 99 successful steps just to retry the failed 100th step.
    *   **The Check-Then-Act Guarantee**: Blindly firing a mutating request without verifying the prior state is strictly forbidden. An Atom must check if an INSERT or File Append is already present. If yes, it yields `SUCCESS` and skips mutation. **CRITICAL (Concurrency)**: Any `Check-Then-Act` Atom mutating shared external state MUST declare an Engine-level `requires_lock` or use atomic remote DB constraints (e.g., `INSERT ON CONFLICT DO NOTHING`) to prevent Fan-Out race conditions.
    *   **Unsafe / At-Least-Once (Ghost Writes)**: For actions that truly cannot be observed post-facto (e.g., sending an Email without an idempotency key), we abandon perfect rollbacks. Sending an email twice is an infinitely smaller price to pay compared to distributed rollback complexity. These Atoms MUST explicitly flag their `AtomResult` with warning metadata (`warning: "At-Least-Once execution detected, possible duplicate"`) to ensure the intent is traceable in the Audit Log without stopping the flow.
6.  **Isolated Fault Domains**: Atoms catch all internal exceptions and yield a structured state (`AtomResult`), preventing Orchestrator crashes.
7.  **Typed Contracts**: Atoms strictly define their required Config (static) and Context (runtime) schemas.

## 2. The Base Protocol (`Atom`)
Located at: `src/flow/atoms/__init__.py`

All Atoms must inherit from this Abstract Base Class.

```python
from enum import Enum
from abc import ABC, abstractmethod
from typing import Any, Dict, Optional

class AtomStatus(str, Enum):
    SUCCESS = "SUCCESS"               # Action completed as intended
    FAILED = "FAILED"                 # Action failed permanently
    RETRY = "RETRY"                   # Transient failure, Engine should retry based on strategy

class RetryStrategy(str, Enum):
    IMMEDIATE = "IMMEDIATE"           # Retry instantly without waiting
    BACKOFF = "BACKOFF"               # Exponential backoff (e.g., 429 Rate Limits). MUST write absolute `next_retry_at` UTC timestamp to state DB to survive orchestrator crash-loops without DDoSing targets.

class AtomResult:
    def __init__(
        self, 
        status: AtomStatus, 
        message: str, 
        exports: Optional[Dict[str, Any]] = None,
        error: Optional[Dict[str, Any]] = None,
        retry_strategy: Optional[RetryStrategy] = None,
        compensating_action: Optional[Dict[str, Any]] = None
    ):
        self.status = status       # The state machine transition signal
        self.message = message     # Human-readable summary for logs
        self.exports = exports or {} # Data to write back to the Global Flow Context
        self.error = error         # Structured error context for debugging/telemetry
        self.retry_strategy = retry_strategy # Instruction on how to retry
```

> **CRITICAL: Context Memory Limits (OOM Prevention)**
> To prevent massive dictionaries from lagging the Engine's disk-syncing loop, `exports` must **never** contain large strings (e.g., full source files, multi-megabyte LLM context dumps).
> *   **Limit**: Direct string payloads inside `exports` should be capped at `128KB` aggregate. This limit also practically applies to large arrays or deeply nested JSON objects. Massive context payloads will silently lag the synchronous state persister.
> *   **Blob Pointers**: For large outputs, the Atom must write the string safely and deterministically to `.flow/artifacts/blob_{Run_ID}_{OutputKey}.txt` and return a lightweight pointer in `exports`. This ensures Blob IO operations are inherently idempotent. If the Atom encounters an `IOError` (e.g., Disk Full), it MUST catch it and yield `FAILED`.
> *   **Implicit Garbage Collection**: Because Blobs use deterministic hashes matching the `Run_ID`, any Orchestrator crash and subsequent retry loop will automatically overwrite the orphaned blob. This entirely eliminates the need for expensive O(N) Mark-and-Sweep garbage collection routines during engine startup. Normal pruning happens on `COMPLETED`/`CANCELLED` states.

```python
class Atom(ABC):
    @abstractmethod
    def run(self, context: Dict[str, Any], config: Dict[str, Any]) -> AtomResult:
        """Executes the discrete unit of work."""
        pass
        
    def cleanup(self) -> None:
        """
        Graceful Teardown Hook (SIGINT/SIGTERM/Pause).
        Used STRICTLY for releasing OS-level resources (e.g., closing subprocesses via 
        Job Objects, closing network sockets) when the Orchestrator pauses or is terminated.
        It MUST NOT be used for logical rollback of data. The Engine MUST wrap this call 
        in an independent `try/except` block to guarantee that a failure here does not 
        abort the broader Flow teardown sequence.
        """
        pass

    # Note: The `compensate()` (SAGA Rollback) method has been EXPLICITLY REMOVED.
    # The Architecture team has mandated a shift towards State Reconciliation via the `run()` 
    # method upon restart, rather than brittle imperative reverse-cascading rollbacks.
```

### 2.1 The Context vs Config Split
*   **`config`**: Immutable parameters defined in the Flow YAML (e.g., `retries: 3`, `target_branch: main`).
*   **`context`**: Malleable runtime state populated by previous Atoms in the pipeline (e.g., `previous_step_artifact_path`). 

> **CRITICAL: Strict Schema Validation (Poison Pill Defense)**
> Atoms MUST NOT blindly trust the `context` payload. Because context is dynamically constructed by upstream Atoms (often via LLMs), it is susceptible to "Schema Poisoning" (e.g., receiving a string instead of an expected list). Every Atom MUST run a strict validation block (e.g., Pydantic) on its required `context` keys during the first cycle of `run()`. If validation fails, the Atom MUST immediately catch the validation error and yield `AtomStatus.FAILED` with a detailed schema error message.

## 3. The `AgentAtom` (Cognitive Execution)

While many Atoms will be procedural (e.g., `GitCommitAtom`, `SendNotificationAtom`), the highest-complexity Atom is the `AgentAtom`.

### 3.1 Purpose
The `AgentAtom` acts as an integration "Hull" or "Shell". It does not directly manage LLM APIs or execute raw system commands. Instead, it tightly binds the **LLM Binding System (`01_06`)** and the **Tooling System (`01_04`)** to achieve a dynamic objective. It embeds stochastic Agentic reasoning into a deterministic Flow.

> **Anti-Pattern Warning (Over-Engineering):** Do not create redundant, specialized Atoms for simple LLM queries (e.g., `SingleShotLLMAtom` or `CategorizeAtom`). A "Single Shot" LLM task is simply an `AgentAtom` configured with an empty Toolset and `max_loops=1`. Use configuration, not subclassing, to maintain architectural simplicity.

**CRITICAL: Agents Resolve Tasks via Tools, NOT Subflows**
Agents resolve potentially multiple tasks at once and are not atomic in intent. However, they **do not spawn subflows or call other Atoms**. They exclusively use **Tools** to impose structure and reduce token consumption during their reasoning loops.

Its primary responsibility as an Orchestrator Atom is **State Boundary Management and Idempotency**: isolating the external systems, hydrating the LLM ReAct loop on a resume, and catching exceptions from the external boundaries to prevent Engine crashes. 

### 3.2 Resilience & The ReAct Loop
A ReAct (Reason-Act) loop is stochastic and can run for minutes, consuming multiple Tools. If the Flow Engine stops mid-loop, starting the `AgentAtom` from scratch destroys progress and wastes tokens.

### 3.3 The AgentAtom Contract
To satisfy the Orchestrator's need for discrete state boundaries, the `AgentAtom` must:
1.  **Delegated Thought History (Engine Ownership)**: The `AgentAtom` is stateless and does NOT manage its own LSM buffer, truncate history, or compress its scratchpad. Giving truncation logic to an Atom violates its functional nature. The **Flow Engine** owns the LLM context buffer. The `AgentAtom` acts as a pure functional bridge: it asks the Engine for its context limits, yields outputs/tool calls to the Engine, and relies completely on the Orchestrator for state squashing.
2.  **Re-entrant `run()` via Run ID**: If `run()` is called, it first checks the `context` for existing serialized history. If found, it natively resumes the ReAct loop from the exact point of interruption rather than restarting the prompt. 
    *   **CRITICAL (Tool Exactly-Once Execution & Sub-Run IDs)**: Tools are inherently side-effecting. The `AgentAtom` relies on the Engine's Tool-level transactional checkpointing (as defined in `01_04_tooling_spec`) to prevent duplicate tool execution upon ReAct loop resumption. To achieve this, the AgentAtom MUST generate absolute, deterministic `Sub-Run IDs` (e.g., `hash(AgentRunID + ToolName + ToolIndex)`) for every discrete tool execution to track individual intent and completion. It also relies on the Engine's external structural isolation to guarantee safe concurrent execution.
3.  **Atomic Indivisibility**: The AgentAtom is a single node. Despite taking minutes to run and triggering thousands of tokens, it relies entirely on the Engine for Subflow routing and structural fault tolerance.

### 3.4 Future Proposal: Database-Backed DAG Serialization
Currently, if a system allows dynamic YAML generation for Flow definitions, there is a risk of YAML serialization corruption during hard crashes (Power Loss). 
*   **Near-Future State**: Dynamic topologies or massive state payloads will be moved entirely off disk-based YAML/JSON into an embedded ACID Database (e.g., SQLite WAL or PostgreSQL for remote). This mitigates partial write corruption completely and removes the need for brittle `.yaml.tmp` Atomic file renames.

## 4. Procedural Orchestration Atoms

In addition to `AgentAtom`, a Flow will consist of procedural Atoms handling logic and state. 

### 4.1 `AssertionAtom` (Deterministic Quality Gate)
*   **Purpose**: A hardcoded programmatic check.
*   **Behavior**: Evaluates a strict rule against the `context` (e.g., `coverage_percentage >= 80`). If the rule fails, the Atom yields `AtomStatus.FAILED` and halts the Flow. If it passes, it yields `SUCCESS`.

### 4.2 `TransformAtom` (Data Mapping)
*   **Purpose**: Adapting data between steps without needing an LLM.
*   **Behavior**: Executes a lightweight JSONPath/JMESPath query against the `context` to extract or restructure data, saving the result to `exports`. Acts as glue between standard Atoms.

### 4.3 `WebhookAtom` (System Integration)
*   **Purpose**: Asynchronous system notification or triggering.
*   **Behavior**: Executes a standard HTTP REST call (e.g., to Slack, Jira, or a CI/CD pipeline) based on fixed `config` parameters. Returns `SUCCESS` if the external system acknowledges the webhook.
*   **Idempotency Guarantee**: MUST natively inject a deterministic `Idempotency-Key` header (derived directly from its Orchestrator `Run ID`). 
    *   **TTL Expiration Defense**: If the Flow pauses significantly and restarts, the retried webhook might exceed the external server's idempotency window (e.g. 24 hours), causing a duplicate action. The Engine MUST flag suspended mutating webhooks that exceed their safely restorable TTL as `FAILED_STALE`, demanding manual administrative intervention.

### 4.4 `ScriptAtom` (Subprocess Execution)
*   **Purpose**: Running deterministic, local scripts or shell commands without expensive Agent overhead.
*   **Behavior**: Executes a command defined in `config` (e.g., `pytest`, `npm ci`, `docker build`) within a bounded subprocess. **CRITICAL**: To respect the 128KB Context Memory Limit, raw `stdout` and `stderr` streams MUST be routed to deterministic Blob files (`.flow/artifacts/blob_*.txt`). Only the Blob Pointers and the `exit_code` are mapped into `exports`. Includes a strict timeout to prevent zombie processes.
*   **Safety (Process Supervision & Job Objects)**: MUST execute out-of-process. To prevent Zombie Child Processes upon hard Orchestrator crashes (e.g. `SIGKILL`), the `ProcessManager` infrastructure MUST use OS-level process grouping (Job Objects on Windows, cgroups/prctl on Linux). The OS Kernel will then guarantee fate-sharing and automatically terminate orphaned scripts if the Orchestrator dies.

### 4.5 `GitCommitAtom` (State Checkpointing)
*   **Purpose**: Creating logical, cohesive checkpoints in the version control history orchestrated by the Flow DAG.
*   **Behavior**: Commits the current project state to a local Git repository. This handles Orchestrator-driven commits to ensure semantic Git history (e.g., at the conclusion of a successful subflow), preventing bloat from automated per-Atom micro-commits.
*   **Note vs. Tools**: While `GitCommitAtom` handles Flow-level checkpoints, Agents executing within an `AgentAtom` MAY also create commits using their explicitly authorized `git_commit` Tool (as defined in `01_04_tooling_spec.md`), subject to Tooling RBAC and message validation policies.

## 5. Non-Atoms (Engine Concerns)

To prevent anti-patterns and redundant proxy classes, the following common orchestration needs are explicitly **NOT** Atoms. They are native features of the Flow Engine DAG Router:

1.  **State Suspension (Waiting/Timers)**: Pausing a DAG context while waiting for an external HTTP webhook or a network timer to expire is not "work"; it is an Orchestration mechanic. There are no `AwaitCallbackAtoms` or `TimerAtoms`. The Engine pauses execution natively via special declarative flow steps (e.g., `- type: await_webhook`).
    *   *Stale Waits and Zombie Flows*: Every `WAITING` or `PAUSED_FOR_APPROVAL` state MUST have an Engine-level `TTL`. If the webhook never arrives and the TTL expires, the flow transitions to `TIMED_OUT` (acting as an Exception) to surface to an admin dashboard.
2.  **Sub-Flows**: A Flow calling another Flow is handled by the Engine recursively loading the requested DAG. There is absolutely NO `SubFlowAtom`. Atoms are indivisible and completely ignorant of sub-flows. This hierarchical state management and resumption is fully detailed in `01_09_flows_spec.md`.
    *   *Reconciliation Resumption Principle*: During a Break/Restart scenario, the engine MUST NOT blindly rely on a saved "Instruction Pointer" to spawn a subflow, as the parent might have crashed *after* launching the child but *before* saving its pointer. In a Reconciliation paradigm, the parent MUST first query the Engine checking if a `SubFlow_ID` for that exact DAG node already exists and is `IN_PROGRESS` or `COMPLETED`. If it exists, the parent attaches to it, preventing orphaned duplicate children.
    *   *Deep Resume Hydration Trap*: Atoms inside a Sub-Workflow MUST receive a dynamically re-merged `context` projection upon Engine Resume. The Engine MUST evaluate `Parent_Context_Live + Child_Local_Context_Live` (with the child shadowing the parent) rather than reading from a completely segregated snapshot silo taken when the Sub-Flow was initially launched. This ensures that any Administrative Override fixes applied to the Parent's context while the child was paused are correctly inherited by the child immediately upon unpausing.
3.  **Routing (Switch/Case)**: Determining which execution branch to take based on a variable is a fundamental DAG traversal feature, managed by the Engine.
4.  **Parallelism (Map/Fan-Out)**: Executing a single task concurrently across a list of items is managed by the Engine splitting the execution thread, not by an Atom attempting to manage parallel subprocesses.
5.  **Parallel Fan-In (Reducers) & Orthogonality (No Data Races)**: Merging outputs from multiple parallel branches back into the parent `context` is a structural Engine routing concern. To prevent data race conditions, the Engine MUST enforce that parallel paths are strictly **Orthogonal** (writing to explicit, isolated sub-domains). **CRITICAL**: The Engine MUST explicitly forbid naive deep-merging or flat `dict.update()` of overlapping keys. If `AtomA` exports `{"user_data": 1}` and `AtomB` exports `{"user_data": 2}`, the Engine must treat this as a Schema Collision failure. A subsequent, sequential `ReducerAtom` must be implemented in the DAG to synthesize these isolated results.
    *   *Global Abort Signal*: Atoms performing long-running continuous loops (like `AgentAtom` ReAct loops) in parallel branches need a way to check a `global_abort_signal`. If Branch A fails fatally, Branch B's executing `AgentAtom` should gracefully abort its loop rather than burning tokens for an already-failed parent DAG.
6.  **Distributed Lock Management (Mutex)**: Atoms MUST NOT natively implement or manage distributed locks (e.g. `MutexAtom`). Mutex handling is an Orchestrator/Engine-level concern.
    *   *Lock Reentrancy and the Deadly Embrace*: If a Parent Flow locks `git_repo`, and a Sub-Flow also declares `requires_lock: ["git_repo"]`, it will deadlock itself. Lock ownership must be tied to the explicit `RootInstanceUUID` (or `TriggerEventID`), allowing reentrant locking for child flows, while preventing sibling parallel flows from bypassing the mutex.
    *   *Lock Stealing Edge Cases & TTL Assertions*: If the Engine Host hard-crashes (Power Loss), local file locks (`.lock`) might be left behind. While restarting the Orchestrator might implement lock-stealing via PID checks for local files, if the lock involves a remote API or Database mutex, PID checks are irrelevant. The Engine MUST enforce **absolute TTL (Time-To-Live) assertions** on all locks.

## 6. Lifecycle & Sandboxing Guarantees

Every derived `Atom` must adhere to these guarantees:

### 6.1 Exception Bleeding (The "Iron Wall")
The `run()` method is wrapped by the Engine in an aggressive `try/except Exception` block. If an Atom throws a standard Python error (e.g., `KeyError`, `IndexError`), the Engine catches it, logs a stack trace, and enforces an `AtomStatus.FAILED` state.
*   **Edge Case**: Native `try/except Exception` does not catch `BaseException` (like `SystemExit` or `KeyboardInterrupt`). If an Atom calls `sys.exit(1)` or crashes the host with a C-extension segfault, the Orchestrator will instantly die.
*   **Hardware IO Exhaustion (Fatal Rollback Trap)**: The Engine must treat `OS_RESOURCE_EXHAUSTED` (e.g., `ENOSPC`/Disk Full) as a completely unrecoverable hardware failure. If an Atom fails to write a Blob due to ENOSPC, the Engine MUST freeze immediately. It MUST NOT attempt to execute `compensate()` rollbacks, as those invariably require disk I/O for logging/telemetry and will also fail. 
    *   *Disk Full WAL Corruption Defense*: A Disk Full error requires a pessimistic Engine restart and a forced integrity check on the `.flow_state/` embedded DB upon recovery to prevent the system from resuming from a partial, corrupted execution cache.

### 6.2 Graceful Teardown (Hard Timeout & Recursive Tracing)
If the Flow Engine receives a `SIGTERM` or cancellation trigger, it iterates over the currently active Atom and explicitly calls `cleanup()`. 
*   **Recursive Stack Traversal**: For fractal subflows (e.g., Flow A -> Subflow B -> Atom C), the Engine MUST walk the entire call stack upwards, executing the `cleanup()` hooks of every parent flow container, as parents might hold broad resource locks independent of the leaf Atom.
    *   *Time-Budget Deficit Trap*: The Engine MUST allocate specific "Time Budgets" per stack height, or execute the teardown asynchronously across the stack simultaneously, to ensure a slow leaf Atom does not exhaust the full watchdog window before the Parent Flow releases its critical Mutex.
*   **Network I/O Restriction**: To prevent blocking the Orchestrator's `SIGTERM` teardown, `cleanup()` MUST NOT perform blocking network I/O (e.g., trying to gracefully close a remote session over a dropped VPN). It should exclusively perform local OS-level teardowns (terminating PIDs, freeing memory buffers).
*   **Signal Handling in Threaded Fan-Outs**: If the Engine uses Python threads for parallel Fan-Outs, executing I/O inside a Unix signal handler will throw `RuntimeError: signal only works in main thread`. Signal handlers for `SIGTERM` / `SIGINT` MUST strictly set a `threading.Event` shutdown flag and return. The main engine loop must poll this flag to cooperatively trigger teardown.
*   **Deadlock Prevention & Watchdog Kills**: The Engine MUST execute `cleanup()` handlers under an absolute, iron-fisted watchdog timeout tracking. 
    *   *Internal Timeout*: The Atom's `cleanup()` execution MUST be wrapped in a strict internal timeout (e.g., 2000ms thread/async limit) so the Python process can gracefully exit (code 0) after a best-effort release of resources.
    *   *External Watchdog*: If the internal timeout fails (e.g., C-extension hang), the Engine MUST trigger an uncatchable `SIGKILL` (or equivalent `os._exit(1)`) to decisively terminate the hanging Orchestrator node and prevent Kubernetes zombie states.

## 7. Lineage & Audit Tracking

Because Atoms represent discrete state boundaries in the Orchestrator, they form the natural resolution for Lineage and Audit tracking (documenting who did what, why, and when).

### 7.1 Phase 1: File-Based Audit Log (Current)
To support the V-Next file-based `.flow_state/` system, the Engine enforces an immutable append-only `audit.jsonl` log parallel to the `context.json`.
*   **Mechanism**: Every time an Atom yields an `AtomResult`, the Engine automatically calculates a state diff and appends a structured Lineage Entry. The log is strictly for LINEAGE; micro-step traces from inside `AgentAtom` loops do NOT pollute the audit log and are relegated to ephemeral trace logs.
*   **Payload Example**:
    ```json
    {
      "timestamp": "2026-02-22T23:05:00Z",
      "flow_id": "req-1234.subflow-A",
      "atom_type": "AgentAtom",
      "run_id": "deterministic-hash-abc",
      "state_transition": "WAITING -> SUCCESS",
      "message": "Approved by Human",
      "mutated_keys": ["review_status", "coverage"],
      "correlation_id": "abcd-efgh"
    }
    ```

> *Note: Phase 2 (Database-Backed Event Sourcing) is planned for the roadmap. See `docs/plans/roadmap_2026.md` (Phase 1.5).*

## 8. Future Proposals

### 8.1 Secrets Injection Interface
*   **Problem**: The secure handling of API Keys or passwords is not defined. If Secrets are passed via `config` or `context` maps, they will serialize to disk in `.flow_state/` and emit to `audit.jsonl`, generating a severe security breach.
*   **Proposal**: Introduce a `secrets: Dict[str, SecretString]` mapping directly into the Atom `run()` signature. Combine this with an Engine-level Vault connector that lazily resolves secrets at runtime in memory, explicitly skipping serialization checkpoints.
*   **Pros**: Eliminates the risk of secret leakage in audit logs and on-disk state files. Adheres to zero-trust security architecture.
*   **Cons**: Adds complexity to the Engine router which now needs to actively manage an external vault connection or decrypt mechanism before dispatching Atoms.

### 8.2 D-State (Uninterruptible Sleep) Watchdog
*   **Problem**: `SIGKILL` does not terminate processes stuck in Linux `D-State` (e.g., waiting for an unresponsive remote CIFS/NFS mount). If an Atom performs I/O on a dead mount, the Orchestrator thread will hang completely, ignoring the 2000ms watchdog timeouts.
*   **Proposal**: Isolate Atoms performing intensive raw disk I/O into separate worker processes mapped via IPC (Inter-Process Communication). This allows the main Orchestrator to gracefully abandon the blocking PID entirely if it enters D-State, self-healing the event loop without requiring a host reboot.
*   **Pros**: Guarantees the Orchestrator's event loop will never fatally freeze due to underlying OS mount point failures or hardware latency.
*   **Cons**: Introduces significant IPC overhead and serialization latency for file operations compared to fast in-thread executions.

### 8.3 Code Version Drift Defense
*   **Problem**: In an environment where Flows can pause for days (e.g., awaiting human approval), the underlying Python code for an `Atom` executing the Flow might be updated and redeployed. When the Flow resumes, the cached `context.json` might violate the new code's schema, causing unhandled deserialization crashes.
*   **Proposal**: Introduce a `CodeVersionHash` tracking mechanism into the state database. On resumption, the Engine compares the current code hash against the paused hash. If a drift is detected, it should flag the Flow for manual schema migration or SRE unblocking, rather than crashing the primary event loop.

### 8.4 The "Poison Pill" Context Trap & Administrative Mutation
*   **Problem**: Subflow A completes and exports a schema-violating payload (e.g., a String instead of a JSON Dict). Subflow B resumes, triggers schema validation, and hard fails. The human fixes the code and restarts the Engine. The flow instantly fails again because the static state on disk still holds the broken string.
*   **Proposal (Administrative Override)**: To support the State Reconciliation paradigm, the system MUST provide a CLI tool (e.g., `flow mutate-context <id> --key=foo --del`) to surgically remove or replace corrupted state cache blocks, breaking the Poison Pill cycle without destroying the DAG's cryptographic checksums.

### 8.5 Unified Stale-State Sweeper
*   **Problem**: Wait TTL expiration relies on the workflow eventually being touched.
*   **Proposal**: Add a lightweight background thread to the Orchestrator (or a dedicated cron process) that strictly enforces TTLs on *all* hanging states (`WAITING`, `IN_PROGRESS` exceeding limits) via the central DB. This prevents silent memory/disk leaks and provides an SLA guarantee to business users.
